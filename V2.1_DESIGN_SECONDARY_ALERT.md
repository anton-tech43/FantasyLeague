# V2.1 Design — Secondary alert channel for chicken-egg Vault failures

**Status:** Design only. Not implemented. Not launch-blocking.
**Owner:** Backend (migration + Slack webhook setup).
**Cost estimate:** ~1 hour for Slack webhook path; ~2 hours for fallback APNs path.

## Problem

`check_pipeline_heartbeat()` (migration 037) alerts when `>50%` of `net._http_response` rows in the last hour are non-200. The alert push is sent via `client-error-alert` Edge Function, which itself uses the Vault `cron_service_key` to authenticate. If the same Vault key is the root cause of the failure (the May 11–17 outage pattern), the alert push ALSO fails. The `client_errors` table row is the only durable trail, but it's not visible to a human until someone manually runs `diagnose-matchday` or queries the DB.

Net effect: the silent-failure-detection mechanism's own alert channel shares the failure mode it's detecting.

## Solution shape

Add a second alert path that doesn't depend on the Vault key. Two viable options:

### Option A (recommended) — Slack webhook via Anthropic MCP

The user has authorized the `mcp__b3fe5cc0-9e39-4de7-b6b1-07bc68562385__slack_send_message` MCP connector. A Slack-bound alert channel:

1. Create a dedicated Slack channel `#goaldigger-alerts` in the user's workspace
2. Generate a Slack Incoming Webhook URL (no scopes needed beyond `chat:write`)
3. Store the webhook URL in a NEW Vault entry: `slack_alerts_webhook` (the URL is the secret — the path doesn't need a JWT, it's just `https://hooks.slack.com/services/T.../B.../xxx`)
4. Extend `check_pipeline_heartbeat()` to fire BOTH the existing client-error-alert push AND a Slack POST:

```sql
-- After the existing alert push block in CHECK 2:
BEGIN
  slack_webhook := get_slack_alerts_webhook();  -- new accessor, returns the URL
  PERFORM net.http_post(
    url := slack_webhook,
    headers := jsonb_build_object('Content-Type', 'application/json'),
    body := jsonb_build_object(
      'text', FORMAT('⚠️ GoalDigger cron HTTP health degraded: %s of %s calls failing in last hour. Likely Vault key shape regression. See IOS_GOTCHAS.md #14.',
        http_total_24h - http_200_24h, http_total_24h)
    )
  );
EXCEPTION WHEN OTHERS THEN
  RAISE WARNING 'Slack alert failed: %', SQLERRM;
END;
```

**Why this works as a secondary path:** Slack's incoming webhook accepts the webhook URL as the entire credential. No JWT involved, no Bearer token, no Supabase gateway. If the Vault entry for `slack_alerts_webhook` is malformed, only Slack alerts break — the existing push path keeps working. Orthogonal failure modes.

### Option B — Fallback APNs path with hardcoded key

Add a `dev_alert_devices_fallback` table with a hardcoded APNs token + `.p8` key reference for ONE dev device. The heartbeat alert can use it directly (without going through `client-error-alert`'s Vault-bearer path) by reading the APNs .p8 from the function env and signing a payload directly in `check_pipeline_heartbeat()` (well, the helper Edge Function it calls). More resilient (works even if Slack is down) but heavier — APNs payload construction in PL/pgSQL is awkward.

**Recommendation: Option A.** Slack webhook is cleaner, lower-cost, and the user already has Slack MCP authorized.

## Critical files

- New migration: `backend/supabase/migrations/039_slack_alerts_vault.sql`
    - Adds Vault entry `slack_alerts_webhook` (created via `SELECT vault.create_secret(...)`)
    - Adds SECURITY DEFINER accessor `get_slack_alerts_webhook()`
    - Modifies `check_pipeline_heartbeat()` to dual-fire (existing push + Slack POST)
- `RUNBOOK.md` — add a "Slack alerts setup" section explaining how to create the webhook
- `IOS_GOTCHAS.md #14` — cross-reference: "If the heartbeat alert pings Slack but not push, the issue is downstream of pg_cron — Slack confirms cron is firing the heartbeat. If neither fires, the heartbeat itself didn't run."

## Verification

1. Apply migration 039 to dev DB with a test Slack webhook URL pointing at a test channel
2. Manually run `SELECT check_pipeline_heartbeat()` after artificially making 60% of recent `net._http_response` rows non-200 (insert synthetic 401 rows for testing)
3. Confirm:
    - `client_errors` row gets inserted (existing path)
    - Slack channel receives the alert message (new path)
4. Set the test Vault entry to a malformed URL, repeat — Slack alert should fail with a warning but the `client_errors` insert should still happen, AND the existing push path should still work (this proves the paths are orthogonal)
5. Revert: replace the malformed test webhook URL with the real one before declaring done

## Out of scope for V2.1

- A third alert channel (e.g., email, PagerDuty). Two channels is enough for the launch period; multi-channel alerting is a V3 ops feature.
- A "summary" alert that batches multiple `client_errors` rows into one Slack message per hour. The throttle in `check_pipeline_heartbeat()` already handles this (alerts at most every hour).
- Slack DM to the user vs channel post. Channel post is simpler and the user can configure DMs as Slack notifications.
