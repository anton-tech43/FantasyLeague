## Headline finding: direct Postgres is unreachable from this session — RED, pushed

`psql "$SUPABASE_DB_URL"` hung with no response at all (not even a refusal) and
timed out. Isolated the cause with a raw TCP probe rather than guessing:

| Target | Port | Result |
|---|---|---|
| `aws-1-eu-west-1.pooler.supabase.com` | 5432 (direct) | **timeout**, no response |
| `aws-1-eu-west-1.pooler.supabase.com` | 6543 (pooled) | **timeout**, no response |
| `aws-1-eu-west-1.pooler.supabase.com` | 443 (HTTPS) | **connects fine** |

That pattern — HTTPS reaches the host, any raw Postgres-wire port does not —
plus this environment's own docs ("outbound HTTPS goes through a pre-configured
agent proxy") says this is **this session's environment network policy**
categorically blocking non-HTTPS egress, not a Supabase outage and not a
credentials problem (`SUPABASE_DB_URL` is present and well-formed). Likely
fix: the environment's Network access setting needs a broader access level —
an HTTPS-only allowlist proxy cannot forward a raw Postgres connection no
matter what host is on the list. Change it from the environment's title-bar
menu → Edit → Network access.

**Consequence: almost everything below that this routine is supposed to do
needs direct SQL and could not run this session.** `scripts/db-health.sh`
sections 2–8, `scripts/verify-push-eligible.sh`, and every query in the
`stale-data-audit` skill (managers, squads, team-page prose, season state,
hardcoded lists) all shell out to `psql` against this same pooler host. None
of it is reproducible over PostgREST: the skill's checks are joins,
`jsonb_array_elements`, and aggregates across tables that aren't all exposed
as REST resources, and I was not going to improvise new raw-SQL-equivalent
write paths (e.g. hand-rolled PATCH requests) outside the patterns the two
hard rules and this repo's own scripts already establish — that is a "risky
write" the brief asks me to avoid, not a safe substitute.

**The good news, confirmed independently:** the app itself is NOT down.
`scripts/db-health.sh` section 1 (PostgREST, the actual path the iOS app
uses) answered all four probes in under 1.3s each with real rows (feed,
team page, squad, season state). So this is a sandbox-access gap for this
routine, not a user-facing outage — I did not want to push "backend down"
language that would misrepresent that.

**Pushed** per the hard rule ("DB was unreachable"). One line, pointing here.
