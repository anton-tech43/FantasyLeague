# V2.2 design — follow up to 2 countries + 2 clubs (opt-in)

Detailed implementation plan. **Supersedes the data-model section of the approved
plan** (`~/.claude/plans/glimmering-foraging-jellyfish.md`): grounding the plan in
the actual registration path and ActivityKit behaviour invalidated two of its core
assumptions (see "Why the approved data model changed" below). Everything else in
that plan — the product decisions, onboarding/Settings UX, context switcher reuse —
stands.

## Product decisions (locked)
- Up to **2 WC countries** and **2 PL clubs**, all **equal** (no primary).
- Opt-in box "I want to add my own team as well" on BOTH the WC-country step and the
  PL-club step → reveals a second picker. Also editable in Settings.

---

## Why the approved data model changed

The approved plan said: drop `UNIQUE(apns_token)`, store **one `device_tokens` row
per followed entity**, and rely on "`live_activity_tokens` already supports multiple
per-country PTS rows — no schema change." Verifying against the code, both are wrong:

1. **Registration is a direct PostgREST upsert, not an Edge Function.**
   `APIClient.registerToken` POSTs to `/rest/v1/device_tokens` with
   `Prefer: resolution=merge-duplicates` (`APIClient.swift:207-232`). That upsert's
   conflict target **is** `UNIQUE(apns_token)`. Drop the constraint and every
   already-installed app loses its conflict target → it **inserts a new row on every
   launch** → row explosion + duplicate pushes for the entire un-updated user base.
   We cannot change shipped clients, so the constraint must stay.

2. **A device has exactly one push-to-start token per activity type.**
   `Activity<MatchActivityAttributes>.pushToStartTokenUpdates`
   (`LiveActivityManager.swift:35`) yields **one** PTS token for the whole device, and
   `live_activity_tokens` has `UNIQUE(token)` (migration 062). So that single token
   can hold exactly one `country_id` today — it cannot "already" trigger for two
   countries. (Two countries appearing to work earlier was two devices / a
   re-registration, not one device holding two PTS rows.)

### Chosen model: array columns, keep the unique keys (one row per device)

Add `country_ids TEXT[]` + `team_ids TEXT[]` to `device_tokens`, and `country_ids
TEXT[]` to `live_activity_tokens`. Keep `UNIQUE(apns_token)` and `UNIQUE(token)`.
A device is still exactly one row in each table.

Why this beats row-per-entity on every axis that matters here:

| Concern | Row-per-entity (approved) | Arrays (this plan) |
|---|---|---|
| Shipped-app registration | **Breaks** (lost conflict target) | **Untouched** — same upsert, just more columns |
| Double-push when a device follows BOTH teams in one fixture (Norway v Sweden; Arsenal v Spurs derby) | Two rows match → needs dedup in every push fn | **Impossible** — one row, one push |
| Token-expiry deactivation (410/400) & GDPR delete (by `apns_token`) | Must fan out across N rows | One row — current code stays correct |
| New Edge Function (`register-follows`) | Required | **Not needed** — direct upsert sends full arrays |
| Push-query change | Filters mostly unchanged | Add an OR-array clause at each read site |

The cost is the OR-array clause at the read sites — bounded, enumerated below. The
single-row invariant removes the entire class of double-push bugs the approved model
introduced, and removes the need for `register-follows` and a row-split migration.

The arrays are the source of truth for updated apps; the existing scalar
`country_id`/`team_id` stay populated (new app mirrors `array[0]`; old apps write only
scalars). Every push query matches **scalar OR array**, so old-app rows match via the
scalar path and new-app rows via the array path with no trigger and no divergence.

## Phase 0 — schema (migrations)

### 0.1 `device_tokens` arrays — migration `069_device_tokens_multi_follow.sql`
- `ADD COLUMN IF NOT EXISTS country_ids TEXT[]`, `ADD COLUMN IF NOT EXISTS team_ids TEXT[]`.
- One-time backfill so existing (old-app) rows match the new array predicate:
  `UPDATE device_tokens SET country_ids = ARRAY[country_id] WHERE country_id IS NOT NULL AND country_ids IS NULL;`
  same for `team_ids`/`team_id`.
- GIN indexes for the overlap/contains filters:
  `CREATE INDEX ... ON device_tokens USING GIN (country_ids) WHERE is_active;`
  same for `team_ids`.
- Keep `UNIQUE(apns_token)`. **Do not drop it.**

### 0.2 `live_activity_tokens` arrays — migration `070_la_tokens_multi_country.sql`
- `ADD COLUMN IF NOT EXISTS country_ids TEXT[]`.
- Backfill `country_ids = ARRAY[country_id] WHERE country_id IS NOT NULL`.
- GIN index `... USING GIN (country_ids) WHERE kind='push_to_start' AND is_active`.
- Keep `UNIQUE(token)`.

### 0.3 RLS / grants check (substep, not a migration unless it fails)
Confirm the anon role can write the new columns. Table-level `GRANT INSERT/UPDATE`
covers columns added later, and the `device_tokens_insert/update` RLS policies are
row-level, so this should already work — but verify with a sandbox upsert that sets
`country_ids` before shipping the client.

## Phase 1 — push read-query rewrites (one row per device → no dedup needed)

For each site: add an OR clause matching the array. PostgREST operators: `cs` =
contains (`array @> {x}`), `ov` = overlap (`array && {a,b}`).

### 1.1 `notification-sender/index.ts:197` — content push for entity `X`
- Now: `.or("team_id.eq.X,country_id.eq.X")`
- New: `.or("team_id.eq.X,country_id.eq.X,team_ids.cs.{X},country_ids.cs.{X}")`

### 1.2 `match-watcher/index.ts:247` — WC goal/HT/FT to playing `[home, away]`
- Now: `.in("country_id",[home,away])`
- New: `.or("country_id.in.(home,away),country_ids.ov.{home,away}")`
- **Perspective copy:** body is keyed by the follower's country (`copy.bodies[...]`).
  With arrays, select `country_id, country_ids` and pick the *playing* one:
  `playing = (country_ids ?? [country_id]).find(c => c===home || c===away)`, use
  `copy.bodies[playing]`. If a device follows BOTH playing countries (they face each
  other), `find` returns `home` first → one push, home perspective. (Neutral
  "your two teams meet" copy = copy follow-up, not blocking.)

### 1.3 `morning-push/index.ts:144` — game-day for `[home, away]`
- Add `team_ids.ov.{home,away},country_ids.ov.{home,away}` to the existing `.or(...)`.
- Same playing-entity pick for the body.

### 1.4 `matchday-reminder/index.ts:67` — "which countries have followers?"
- Now: select `country_id` where not null.
- New: select `country_id, country_ids`; build the Set from both
  (`for (r) { if (r.country_id) add; (r.country_ids ?? []).forEach(add) }`).

### 1.5 `matchday-reminder/index.ts:180` — reminder push for country `C`
- Now: `.eq("country_id",C)`
- New: `.or("country_id.eq.C,country_ids.cs.{C}")`

### 1.6 Token lifecycle — **no change**
`notification-sender:326/332` (deactivate on 410/400 by `apns_token`) and
`delete-my-data:40` (delete by `apns_token`) stay correct: one row per token.

## Phase 2 — Live Activity (single PTS token, multiple countries)

### 2.1 `match-watcher/index.ts:1040` — PTS start for `[home, away]`
- Now: `.eq("kind","push_to_start").in("country_id",[home,away])`
- New: `.or("country_id.in.(home,away),country_ids.ov.{home,away}")` (after 0.2).
- One PTS row per device → one start → one Live Activity per match. `:1030/:1062`
  (update/end by `fixture_id`) unchanged.

### 2.2 `LiveActivityManager.swift:45` — register PTS with all followed countries
- Send `country_ids = AppState.shared.selectedCountries.map(.rawValue)` (and keep
  `country_id = first` for back-compat) via `registerLiveActivityToken`.
- Re-register on the followed-country set changing (mirror the alert-token re-register).

## Phase 3 — registration client (`APIClient` + `NotificationService`)

### 3.1 `APIClient.registerToken`
- Accept `countryIds: [String]`, `teamIds: [String]`.
- Body: `country_ids`, `team_ids` (always the FULL arrays so a *removed* follow is
  dropped by the merge-duplicates replace), plus scalar `country_id = countryIds.first`,
  `team_id = teamIds.first` for back-compat. Keep `merge-duplicates`.
- `registerLiveActivityToken`: add `countryIds` → `country_ids` (+ scalar first).

### 3.2 Retire the partial PATCH helpers
`updateTokenCountry`/`updateTokenTeam` (`APIClient.swift:262-287`) become a full
re-register (send the complete arrays). One write path; removal works for free.

### 3.3 `NotificationService`
- `lastRegisteredScope` = `sorted(countryIds + teamIds).joined("|") + "|" + tier`.
- `reregisterForFollowChange()` recomputes the set and calls `registerToken` +
  `LiveActivityManager.registerPushToStartIfPossible()`.

## Phase 4 — iOS model + UI

### 4.1 `Models/AppState.swift`
- `selectedCountry: Country?` → `selectedCountries: [Country]` (cap 2);
  `selectedTeam: Team?` → `selectedTeams: [Team]` (cap 2). Persist as JSON arrays.
- First-launch migration: read legacy `selectedCountry`/`selectedTeam` keys into the
  arrays. Keep `var selectedCountry: Country? { selectedCountries.first }` style
  convenience accessors so single-entity call sites compile unchanged.
- Add the array keys to `clearAllData`.

### 4.2 Onboarding
- `CountrySelectionView` / `OptionalPLTeamView`: after the first pick, show the opt-in
  "add my own country/club too" box → reveals a 2nd picker (cap 2).
- `CountrySelectionView` is reused by Settings + WCMigration → gate the multi-pick
  behind a `allowsSecond: Bool` parameter so those callers stay single-pick unless opted in.

### 4.3 Settings (`SettingsView.CountryPickerSheet`)
- Country/club rows become a small managed list (add/remove the 2nd); on change call
  `reregisterForFollowChange()`.

### 4.4 Context switcher (`ContextSwitcherView`) — minimal
- Feed it `selectedCountries + selectedTeams + Everyone`. It already iterates a list,
  so each entity is its own tab; feed + unread already key on the active context.

### 4.5 Calendar (`CalendarSyncService`)
- Sync the union of followed entities' fixtures.

## Phase 5 — verification matrix
- **Register:** tick "add my own country", pick Sweden alongside Norway → DB shows ONE
  `device_tokens` row with `country_ids = {norway,sweden}` (not two rows). Same for clubs.
- **Push, disjoint fixtures:** Norway plays → device alerted (Norway perspective);
  later Sweden plays → device alerted (Sweden perspective).
- **Push, head-to-head (the dedup case):** Norway v Sweden → device gets **exactly one**
  alert (home perspective), one Live Activity. Arsenal v Spurs (both followed) → one
  morning push, one content push.
- **Switch:** each followed entity is its own feed tab.
- **Remove:** drop Sweden in Settings → re-register sends `country_ids={norway}`; the
  Sweden overlap no longer matches → Sweden pushes stop, Norway continues.
- **Old app (regression):** an un-updated install still registers (UNIQUE intact),
  still matched via the scalar clause, still gets exactly one push.

## Copy-framing follow-up (not blocking)
Generated content is framed around the primary relationship + name (D1: "ask him…").
An *added own* team has no "his"; for now it flows through the same pipeline carrying
that framing. Neutralizing copy per followed-entity (and a "your two teams meet" line
for head-to-heads) is a separate content change — flag, don't block.

## Rollout order
0 (migrations, additive — safe live) → 1 + 2.1 (backend reads; arrays already
backfilled so behaviour is identical until a client writes a 2nd entity) → deploy →
3 + 4 + 2.2 (iOS, ships in a build). Backend is forward-compatible: it reads arrays
that only ever have one element until the new app ships, so Phase 0–2 can go live
ahead of the app with zero behaviour change.
