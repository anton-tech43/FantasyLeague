Six models of a system that mostly isn't code

Everything GoalDigger shows a person is produced by something on a clock. There are three kinds of clock — pg_cron inside Postgres, the claude.ai routine scheduler, and one event path from the live-match engine — and they bill two different wallets. The rule, and the day it was written

On 20 May 2026 a 50-team backfill through team-page-generator burned $4–5 of API credits in a few minutes and bottomed the account. The same work was available for nothing, because the data was already in raw_fetch_logs.

The standing rule: never loop a paid API call across teams. For any cross-team change, the order is SQL first, then a one-off routine, and only then an Edge function. team-season-state-generator still carries a warning in its header that a call with no team_id loops inference over every team.

Two quota ceilings on the routine side

25 remote runs per day. A four-match Saturday already budgets about 19 of them. And roughly 30 fires per rolling hour, per routine — undocumented anywhere, discovered as HTTP 429s in the production log on 12 September. Any design that fires once per club breaks the first ceiling before it reaches the second.

What the model is given, and what it is told to ignore

Every payload from an external source is wrapped in an <external_data trust_level="untrusted"> fence, and the system prompt says embedded instructions inside that fence must be ignored. Our own data — the squad's season, the league table — is handed over outside the fence, because it is the record rather than someone's narrative.

Two grounding rules override the RSS entirely. A scoreline comes from fixtures_last.score.fulltime, never from match-report prose. A player's standing comes from the players table, never from how a transfer story framed him.

For the AI engineer

The guard ladder

The validator's design principle is counter-intuitive and was learned expensively: a card that never publishes is usually the worst outcome. Replaying 1,019 cards through reject-only guards published 99 of them. Through the repair-first ladder, 1,012.

TierWhat belongs hereBehaviour
1 · AUTO-FIXAnything mechanically repairable: length caps, lowercasing, terminal punctuation, dash glyphs, house copy substitutions, card shapeApplied silently and logged. Never blocks.
2 · quality_failVoice and craft. Burned phrases, a talking point that interrogates her, two points saying the same thing, a missing analogyRejects on attempt 1 with a rewrite instruction. Publishes anyway on attempt 2, violation recorded.
3 · hard_failUnsafe or untrueNever publishes. Any attempt.

Push-eligibility downgrades

A separate mechanism from rejection: the item publishes to the feed and simply never pushes. Seven of them, and they encode product judgement rather than correctness — a non-football celebrity reaction, a player's international duty written for his club feed, quiet hours between 21:00 and 06:00 UTC, an unconfirmed transfer rumour, an opaque teaser headline, and a full-time article whose push already went out.

The two failure classes no guard catches

A true sentence about the wrong person. On 30 September the "ones to know" card was naming players who were not playing — 20 of 60 picks outside their own squad's top fifteen by minutes, one of them a goalkeeper with no minutes at all. Every guard passed, because nothing on the card was false. A source can be accurate, current and complete and still produce something useless if it does not carry the dimension the surface is actually about.

Cards that never existed. Every audit measures what shipped; none can see what did not. A 38-character title against a 35-character database constraint silently killed every Champions League qualification card, and nobody noticed, because the thing to notice was an absence.

Testing them

Every guard is tested both ways — one payload that must be rejected, and the legitimate payload it must not catch. The convention exists because the failure actually hit was a rule so strict it rejected correct house style. bash test_guards.sh runs 111 assertions offline in about a minute, with no network and no writes.

What the shipped key can do

The app authenticates with a publishable key compiled into the binary. It can SELECT from 13 content tables and call exactly three functions — registering a device token, registering a Live Activity token, and saving a user's match predictions. It cannot insert, update or delete anything, anywhere.

The thing to know before you write a new database function

Supabase's default privileges grant anon an explicit permission on every new table and function in public. A REVOKE ... FROM PUBLIC does not touch an explicit grant, so four separate migrations wrote a revoke, read as though they had closed a function, and left it callable with the key that ships in the App Store binary.

Worse: for functions this cannot be fixed by changing the default at all. Both documented forms were tested against this database and a freshly created function still came out callable. Every CREATE FUNCTION needs its own explicit revoke, and the only defence is noticing — which is what section 7 of db-health.sh does.

The one script to run when something looks wrong

./scripts/db-health.sh runs from outside, over the same public internet the app uses, with the app's own key. Eight sections, and the first two exist to answer a question nothing else could: on 21 September the Supabase dashboard reported the database unhealthy for an hour while Postgres answered every query — PostgREST had fallen over, and the two look identical from the app. Section 8 asks whether the content is true, which is a different question from whether the jobs ran, and was added after a wrong card survived a month with every job reporting green.

The smoke alarm has no one to call

dev_alert_devices has zero rows. client-error-alert works — it is called by notification-sender on every APNs auth failure — but every alert it has ever raised went nowhere. On 2026-09-19 and 2026-09-20 it recorded pg_cron HTTP health degraded: 185 / 200 calls in last hour returned non-200 (93% failure) and told nobody. The cause is one level down: register-dev-device, the function that would put a phone on that list, has no call site in the current app. This is the most actionable thing on this page — one row in one table turns the alarm back on.

Why nobody was pushed for a whole Premier League matchday — now known

Four fixtures kicked off on Sunday 20 September and match_status_state recorded none of them. The cause was in client_errors the whole time: 57% of scheduled HTTP calls failed on the 19th, 93% on the 20th. The system detected its own outage, wrote it down, and had no recipient — see above. It is not reproducing: the scheduler answers every minute today and the league-picker correctly returns the Premier League for 10 and 11 October. Watch the first fixtures after this, and keep db-health.sh §8i in the loop.

A freshness guard that inverted into the bug it was written to prevent

team_season_state looked a month dead. It was not: the writing underneath was nightly and correct. post_season_state.sh only stamps the freshness column when the payload carries prose, and that test named summary — a field the prompt had been redesigned to stop producing in the same week. So from the day the guard was added, every write took the other branch and the timestamp froze. Fixed to name the fields the prompt actually emits, with test_season_state_stamp.sh behind it so it cannot drift silently again.

“Is the live pipeline broken, or is nobody playing?”

Those look identical and the difference cost an hour here and an inconclusive paragraph in the 5 October content review. db-health.sh section 8i now answers it from the fixture cache. Its first draft cried wolf on a Crystal Palace friendly, which is the third time a check in that section has been broader than the rule it was auditing — it now uses the same covered-competition set the watcher itself polls.

The routines README contradicted itself twice

It said “6 Premier League teams” (there are 20) and gave gd-news two different schedules in two sections. Settled against production — the log shows two runs a day, at 06:xx and 22:xx UTC and no other hour — and both corrected.
