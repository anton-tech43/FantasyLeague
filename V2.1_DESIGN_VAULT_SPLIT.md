# V2.1 Design — Two-Vault-entry split for cleaner key rotation

**Status:** Design only. Not implemented. Not launch-blocking.
**Owner:** Backend (migration + Vault config + Edge Function env update).
**Cost estimate:** ~1 hour to ship.

## Problem

Today, ONE Vault entry `cron_service_key` serves two distinct authentication purposes:

1. **Edge Function INVOCATION** — pg_cron and any external curl that calls an Edge Function via `POST /functions/v1/<name>` with an `Authorization: Bearer <key>` header. The Supabase gateway runs `verify_jwt` on this header BEFORE invoking function code, so it MUST be JWT shape (`eyJ...`, three base64 segments).

2. **Function-internal PostgREST writes** — the `SUPABASE_SERVICE_ROLE_KEY` env var that Edge Function code uses to authenticate against the Supabase REST API for data writes. PostgREST accepts both the legacy JWT shape AND the new `sb_secret_*` opaque format.

Both keys live in the same Vault row. If the row is updated to the wrong shape (the May 11-17 outage cause: someone updated Vault to the new `sb_secret_*` format key, which PostgREST accepted but the Edge Function gateway rejected), the **cron-driven half of the pipeline silently dies** while function-internal writes keep working. The mixed-purpose Vault row hides this: anyone inspecting the Vault sees "key looks valid" because PostgREST is happy, even though the gateway is silently 401-ing every cron tick.

## Solution shape

Split into two Vault entries with explicit purposes:

```sql
-- Vault entry 1: Edge Function INVOCATION bearer.
-- MUST be legacy JWT format (eyJ...). Used by pg_cron and any external
-- script that posts to /functions/v1/<name>.
SELECT vault.create_secret(
  '<legacy service_role JWT, eyJ... 219 chars>',
  'bearer_token_for_edge_functions',
  'JWT-shape token for Edge Function gateway. NEVER replace with sb_secret_* — gateway rejects opaque tokens with 401 INVALID_JWT_FORMAT.'
);

-- Vault entry 2: PostgREST data-writes service role.
-- Can be EITHER legacy JWT OR new sb_secret_*. Used by Edge Function
-- internal code via SUPABASE_SERVICE_ROLE_KEY env.
SELECT vault.create_secret(
  '<service_role key in either format>',
  'postgrest_service_role',
  'Service-role key for PostgREST data writes. Accepts JWT or sb_secret_* format. Rotate independently of bearer_token_for_edge_functions.'
);
```

Then:

```sql
-- Modify the SECURITY DEFINER accessor to read from the new entry:
CREATE OR REPLACE FUNCTION get_cron_service_key()
RETURNS TEXT
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = ''
AS $$
DECLARE
  k TEXT;
BEGIN
  SELECT decrypted_secret INTO k
  FROM vault.decrypted_secrets
  WHERE name = 'bearer_token_for_edge_functions';
  -- Belt-and-braces shape check: if Vault was rotated to the wrong shape,
  -- raise immediately rather than letting cron silently 401.
  IF k IS NULL OR LEFT(k, 3) != 'eyJ' OR LENGTH(k) < 100 THEN
    RAISE EXCEPTION 'bearer_token_for_edge_functions is not JWT shape (prefix=%, len=%). Gateway will reject every cron tick.', LEFT(k, 3), LENGTH(k);
  END IF;
  RETURN k;
END;
$$;
```

The Edge Function env vars stay unchanged — `SUPABASE_SERVICE_ROLE_KEY` continues to be the new `sb_secret_*` format key set by Supabase platform. The Edge Function code never reads from `bearer_token_for_edge_functions` (it doesn't need to — it has the env var). The cron commands read from Vault via the accessor.

## Critical files

- New migration: `backend/supabase/migrations/040_vault_split_bearer_vs_postgrest.sql`
    - Creates the two new Vault entries (the old `cron_service_key` row is left in place during transition for one release, then deprecated in 041)
    - Updates `get_cron_service_key()` to read from `bearer_token_for_edge_functions` with the new shape check
- `scripts/verify-cron-auth.sh` — already does the JWT-shape check; now also pings `bearer_token_for_edge_functions` by name (was: `cron_service_key`). Update the name in the script.
- `IOS_GOTCHAS.md #14` — update the "Vault key shape" gotcha to reference the new entry names. Mention that `postgrest_service_role` can be either format and that pg_cron-only failures point at `bearer_token_for_edge_functions`.
- `RUNBOOK.md` — update the "Push pipeline health check" SOP section that mentions Vault to use the new entry name.

## Verification

1. Apply migration 040 to dev DB
2. Run `./scripts/verify-cron-auth.sh` — confirms all 4 checks pass against the new entry name
3. Invoke `check_pipeline_heartbeat()` manually — confirms it can still pull the bearer via the updated accessor
4. Smoke-test cron firing: wait for next `match-watcher` minute-mark, check `net._http_response` returns 200 (proves the new accessor is wired correctly into the cron commands)
5. Inspect Edge Function logs — confirm no Edge Function is reading from `cron_service_key` directly (search the codebase: should only `get_cron_service_key()` reference Vault). If any function reads the OLD entry directly, it'll start failing at this migration boundary.
6. Set `bearer_token_for_edge_functions` to a deliberately wrong shape (the new `sb_secret_*` format) — confirm `get_cron_service_key()` now RAISES EXCEPTION immediately rather than returning the bad value. This is the new safety net.
7. Revert: put the legacy JWT back in `bearer_token_for_edge_functions`.

## Migration safety

Don't delete `cron_service_key` in this migration — leave it for one release as a fallback. The migration adds the two new entries and updates the accessor. After confirming 040 is stable in production for a week, a follow-up migration 041 can `vault.delete_secret('cron_service_key')`.

## Out of scope for V2.1

- Token rotation automation (rotating bearer tokens periodically). Manual rotation per Supabase guidance is fine for solo-developer scale.
- Multi-environment Vault entries (dev/staging/prod). Single-environment is fine until the project scales beyond one DB.
- HSM-backed Vault. Supabase Vault uses libsodium under the hood — that's already cryptographically sound for our threat model.
